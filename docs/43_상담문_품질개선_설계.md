> 이 명식에서 먼저 확인할 것은 일을 시작하는 속도보다 끝내는 기준이오. 표현하고 고치는 쪽이 준비하고 받아들이는 쪽보다 많이 잡혀 있소. 그래서 ‘더 배워야 움직이는가’보다 ‘이미 만든 것을 계속 고치고 있는가’를 먼저 묻겠소.

>
> 같은 수정이라도 이유는 나눠 봐야 하오. 약속한 기준을 맞추는 수정인지, 그대가 더 잘하고 싶어 덧붙이는 수정인지 말이오. 두 가지가 섞이면 결과물은 좋아져도 마감과 보수는 처음 약속에 묶여 있을 수 있소.
>
> 다음 작업에서는 시작 전에 ‘이 세 가지가 되면 전달한다’고 적어 보시오. 나중에 발견한 개선점은 다음 작업에 쓸 목록으로 따로 남기시오. 완성도를 버리라는 뜻이 아니오. 이번에 약속한 일과 다음에 더 잘할 일을 구분해 보자는 말이오.
>
> 만약 수정이 늘어나는 이유가 상대의 잦은 요구 변경이라면, 그대의 끝내는 버릇보다 작업 조건을 먼저 봐야 하오. 그때는 수정 횟수와 추가 일정부터 다시 합의하는 편이 이 설명에 더 맞소.

## 생성 구조

1. 계산 결과를 사실 목록으로 만든다. 기둥·십신·위치·비중·기존 강약·운과 원국의 관계·시각 불확실성을 ID와 함께 보존한다. 사용자 경험과 계산 사실은 별도 필드다.
2. 해석 계획을 만든다. 중심 가설 하나, 이를 뒷받침하는 사실, 반대 근거, 적용 조건, 아직 모르는 경험, 확인 질문을 고른다. 단순 공존이나 최다 십신 하나로 모든 영역을 설명하지 않는다.
3. 전체 상담문을 작성한다. 특징의 상호작용에서 생활 장면과 비용을 설명하고, 조건에 맞는 행동으로 이어 간다. 기운별 설명을 차례로 붙이지 않는다. 전문 근거는 별도로 펼쳐 읽게 한다.
4. 검수 후 렌더링한다. 사실 ID 유효성·숫자 일치·거절한 가설 재등장·사용자 답변 왜곡·권한·HTML 안전성을 코드로 검사한다. 의미상 비약과 상투성은 별도 원고 검토로 검사한다. ID가 맞는다는 사실만으로 해석이 타당하다고 판정하지 않는다.

실제 모델 경로는 사용 여부 결정 후 구현한다. 모델에는 계산을 맡기지 않으며, 확정된 서버 사실과 필요한 상담 답변만 제공한다. 공급자 선택·모델명·호출 비용·보관 설정은 구현 때 확인한다. 정상 생성과 규칙 기반 대체 결과를 내부에서 구분하고 모델 실패를 고품질 생성 성공으로 기록하지 않는다.

## 검증 설계

동일 입력의 기존 원고와 새 원고를 이름을 가리고 비교한다. 30개 합성 명식과 6개 고민을 시작 표본으로 쓰되 개선율의 통계적 근거로 삼지 않는다.

- 반대 비중: 4:1을 1:4로 바꾸면 핵심 해석과 조언의 방향이 달라지는가?
- 위치 차이: 수가 같고 월지·일지 배치가 다를 때, 지원된 해석 범위 안에서 설명이 달라지는가?
- 고민 변경: 돈과 연애가 제목만 바뀐 글로 나오지 않는가?
- 경험 변경: 내 선택과 외부 요구를 바꾸면 원인 설명과 행동이 함께 바뀌는가?
- 거절·초기화: 부정한 가설이 비유나 다른 캐릭터를 통해 되살아나지 않는가?
- 불확실성: 시각 미상과 근거 부족을 성격 단정으로 채우지 않는가?
- 독자 비교: 더 구체적인 문장, 일반적인 문장, 틀린 추정, 실제로 해볼 행동을 직접 표시하게 한다.

자동 검사는 오류를 막는 장치다. 새 모델의 자기 평점과 내부 체크리스트만으로 품질 향상을 선언하지 않는다. 실제 독자 비교와 명리 규칙 검토의 결과는 별도로 기록한다.
