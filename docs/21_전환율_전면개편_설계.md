작성일: 2026-09-08. 대상: 모바일 신규 방문자 1만 명. 상태: 코드 감사 + 연구 + 구현 명세 + 인터랙티브 시안. **운영 반영·배포·실사용자 실험 완료 문서가 아니다.**

## 1. 제품 판단

첫 화면에서 신비로운 세계관을 이해시키기보다 **“내가 반복하는 문제를 읽고, 다음 행동 하나를 얻는다”**를 전달한다. 세계관은 인물·일러스트·한 문장의 말투에 남기고, 입력·가격·오류·환불 안내는 현대 한국어로 쓴다.

결제 이유는 공포나 분량이 아니라 무료 결과에서 확인한 구체성과 유료 결과의 추가 효용이다. 목표는 방문당 첫 결제율과 환불 차감 매출을 함께 높이는 것. 100% 결제나 특정 전환율을 보장할 근거는 없다.

권장 첫 실험은 **고민 중심 첫 화면 + 입력 축약 + 무료 해석 한 편 완결 + 결과 중심 상품 설명**의 일관된 경험이다. 효과가 확인되면 카피, 고양이, 상품 배치를 각각 분리 실험한다. 가격 변경과 전체 시각 개편을 동시에 섞어 원인을 잃지 않는다.

### 점수와 사주 로직을 분리해서 읽기

실행한 내부 검사: 총점 **72**, 개인별 차별화 **43**, 근거 표기 **100**, 아픈 정확도 **55**, 돈값 **74**, 읽기 **100**, 끌림 **93**. 고민 간 82%, 사람 간 62% 겹침은 **공백으로 나눈 단어 집합의 유사도**다. 문장 82%가 복사됐다는 뜻도, 이용자 82%가 불만족한다는 뜻도 아니다. 주 표본은 6명·6고민·월하 렌즈 중심으로 전체 인물과 실제 고객을 대표하지 않는다.

근거 100은 출처·숫자·구분 기호 존재 여부에 가깝다. 아픈 정확도는 일상 단어 등의 출현 비중을 본다. 돈값은 가격과 분량의 관계를 포함한다. 이 지표를 맞추려고 숫자·생활 단어·글자 수를 늘리면 실제 품질이 악화될 수 있다.

`calendar.py`는 절입·한국 표준시 보정 등으로 기둥을 계산하고, 시간 미상일 때 시주를 제외한다. `features.py`는 오행·신강약·용신·십신·합충·대운·신살 등의 전통 해석용 특징을 만든다. 이것은 **계산 재현성**과 **전통 규칙의 설명 가능성**을 제공하며, 성격이나 미래 예측의 과학적 정확도를 입증하지 않는다.

이번 회귀 확인: `tests/test_calendar.py` **94개 통과**. pytest 캐시 쓰기 권한 경고 1개. 이것만으로 전체 해석 품질·결제 안정성·1만 명 처리 성능을 검증했다고 보지 않는다.

## 3. 연구를 제품에 적용하는 방법

| 근거 | 적용할 장치 | 이 서비스에서 검증할 것 |
|---|---|---|
| [NN/g: 점진적 정보 공개](https://www.nngroup.com/articles/progressive-disclosure/) | 별칭·선택 성향·해석 상세를 필요한 시점에 펼침 | 입력 완료율, 수정 횟수. 계산에 필요한 필드까지 숨기지 않음 |

| [목표 경사 연구](https://www.columbia.edu/~rk566/Session4/Goal-Gradient_Illusionary_Goal_Progress.pdf) | 실제 완료한 3단계 표시, 저장 후 발도장 | 입력 지속에 도움이 되는지. 충성 프로그램 연구를 결제 효과로 단정하지 않음 |
| [Nittono 외: 귀여운 이미지 실험](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0046362) | 전환 순간에 작은 고양이 반응 | 주의·조심스러운 수행 관련 실험이며 구매 증가를 입증한 연구가 아님 |
| [Microsoft: 신뢰할 수 있는 실험](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-during-experiment-stage/) | 실험 배정 이상·데이터 품질·사업 지표·보호 지표 함께 확인 | 클릭만 오른 안을 승자로 채택하지 않음 |

상호성은 무료로 완결된 도움을 제공하는 방식으로, 자기 관련성은 사용자 입력과 조건별 해석으로 구현한다. 손실 회피·호기심은 ‘현재 반복의 비용을 알아보기’라는 질문에 한정한다. 불운 카운트다운, 가짜 잔여 수량, 만들어낸 구매 후기, 결제를 안 하면 고양이가 슬퍼지는 장치는 사용하지 않는다. 장기 신뢰와 환불 차감 매출을 훼손할 수 있다. [FTC의 기만적 설계 보고서](https://www.ftc.gov/news-events/news/press-releases/2022/09/ftc-report-shows-rise-sophisticated-dark-patterns-designed-trick-trap-consumers)는 이런 설계의 문제를 다룬다. 한국 법률에 대한 별도 판단으로 인용하지 않는다.

## 4. 새 사용자 여정과 화면별 카피

### ① 첫 화면: 무엇을 얻는지 5초 안에 이해

브랜드: **성신당 星辰堂**. 상단 보조 문구: **사주로 읽는 나의 반복 패턴**.

제목: **왜 나는 비슷한 일에서\n자꾸 마음이 걸릴까.**

설명: **태어난 정보와 지금의 고민을 바탕으로, 반복되는 패턴과 오늘 해볼 행동을 읽어보세요.**

주 버튼: **내 고민으로 무료 해석 보기**

버튼 아래: **첫 해석 무료 · 태어난 시간은 몰라도 돼요**

작은 설명: **전통 사주를 바탕으로 한 자기 이해 콘텐츠예요.** 소요 시간은 측정 전에는 ‘30초’처럼 약속하지 않는다. ‘1만 명이 봤어요’, 정확도 98%, 후기 별점은 검증 가능한 실제 데이터가 있을 때만 표시한다.

첫 화면에 인물 20명을 나열하지 않는다. 하나의 인물과 작은 고양이, 핵심 문장, 하나의 주 행동. 이미지 전체 클릭으로 다음 단계가 열리는 동작은 제거해 오작동을 막는다.

### ② 고민 선택: 원하는 답을 먼저 말하게 하기

제목: **지금 가장 알고 싶은 건 무엇인가요?**

선택지: 연애·관계 / 일·커리어 / 돈·소비 / 방향·선택 / 마음·생활 리듬 / 지난 관계.

세부 질문 한 개는 선택 사항. 예: 관계 → ‘내가 더 애쓰는 느낌’ / ‘마음을 표현하기 어려움’ / ‘아직 잘 모르겠음’. 기존 concern 코드에 매핑하고 코드·콘텐츠 버전을 관리한다. 건강 concern은 질병 판정 대신 생활 리듬의 범위를 명시한다.

버튼: **이 고민으로 이어가기**. 선택 카드 자체로 다음 화면에 즉시 넘어가지 않으며 수정할 수 있다. 상단 ‘1/3 고민 선택’은 실제 현재 단계다.

### ③ 출생정보: 한 화면, 모르는 정보는 정직하게

제목: **해석에 필요한 태어난 정보를 알려주세요.**

생년월일 + 양력/음력, 시간 입력 또는 **시간을 몰라요**, 계산에 필요한 성별 기준과 출생지. 기존 엔진이 지원하는 범위·보정 정책을 그대로 사용한다. 출생지는 설명 아래 접을 수 있어도 잘못된 기본값을 몰래 확정하지 않는다. 성별 입력이 전통 대운 방향 계산에 쓰인다는 이유를 안내하고, 미입력 지원은 엔진 정책 결정 후 구현한다.

별칭과 네 글자 성향은 결과 저장/심화 해석 때 선택하도록 뒤로 옮긴다. 필수처럼 보이는 optional 필드를 만들지 않는다. 오류는 해당 필드 바로 아래, 입력값 유지, 첫 오류로 초점 이동. 생일을 틀렸다고 전체 화면을 초기화하지 않는다.

버튼: **무료 해석 보기**. 안내: **시간을 모르면 시주를 제외한 범위에서 해석해요.** 개인정보 사용·보관 안내는 서비스의 실제 정책과 일치시키며 ‘저장하지 않아요’를 확인 없이 쓰지 않는다.

계산 중: **입력한 정보로 명식을 계산하고 있어요.** 실제 작업 상태로 표시하고 완료되면 바로 이동한다. 인위적으로 기다리게 하거나 실제 없는 단계에 진행률을 붙이지 않는다. 실패 시 재시도와 정보 수정 제공.

### ④ 무료 결과: 하나는 끝까지 도와준다

상단: ‘관계 · 무료 해석’, 입력 정보 수정, 시간 미상 표시. 읽기 순서:

1. **핵심 한 문장**: 조건부로 생성한 행동 패턴.
2. **구체적 장면**: 사용자 선택과 연결된 생활 예시 2~3문장.
3. **왜 이렇게 읽었는지**: 전통 해석 규칙과 입력 출처를 접어서 설명.
4. **오늘 해볼 행동 하나**: 돈을 내지 않아도 실행할 수 있는 완결된 도움.
5. **“이 장면이 내 경험과 가까운가요?”** 가까워요 / 달라요 / 아직 모르겠어요.

‘달라요’는 정답을 회피한다고 해석하지 않는다. 다른 상황을 고르거나 해석을 건너뛸 수 있게 한다. 공감 응답을 받아놓고 최초 예측이 맞았다고 집계하지 않는다.

무료 결과의 마지막: **이 패턴을 바꾸려면, 어떤 말을 먼저 꺼내야 할까요?** 아래에 유료에서 새롭게 제공할 답 3개와 실제 일부 샘플. 핵심 해석 전체에 블러를 씌우지 않는다.

### ⑤ 상품 + 주문 확인: 내용, 금액, 열람 조건을 한 번에

제목: **읽고 끝내지 않고, 다음 행동까지.**

관계 예시의 추가 답: **반복이 시작되는 상황 / 관계에서 세울 기준 / 실제로 꺼낼 말과 피할 말**. 이 목차는 새 콘텐츠 제작 명세다. 기존 리포트에 내용이 없으면 먼저 제작·검수해야 하며 카피만 바꿔 제공한다고 주장하지 않는다.

추천 이유: **관계 고민을 선택해서 월하의 해석을 먼저 보여드려요.** ‘당신에게 가장 정확한 인물’처럼 확인하지 못한 비교는 쓰지 않는다. 추천 변경 및 전체 인물 보기 제공.

월하 현행 예시: **월하 해석 · 15,900원 · 한 번 결제 · 영구 열람**. 이름·가격·실제 열리는 챕터는 서버가 반환한다. 하단 결제 버튼: **15,900원 결제하기**. 환불·열람 조건과 결제 수단 선택은 버튼 근처에서 확인 가능하게 한다. 기존 이용자의 결제 복원 경로를 유지한다.

설명 전문을 읽으려면 별도 중간 페이지를 거쳐야 하는 구조를 줄인다. 구매 전에 묻는 질문을 같은 화면에서 접고 펼친다. 신규 가입 강요와 결제 중 성향 입력은 추가하지 않는다.

### ⑥ 승인·열람·재방문

승인 대기: **결제 결과를 확인하고 있어요. 이 화면에서 잠시 기다려 주세요.** 타임아웃이면 **확인이 지연되고 있어요. 결제 내역 확인 후 다시 안내할게요.** 중복 결제 버튼 대신 주문 상태 확인.

성공은 서버 승인과 권한 부여 확인 후 표시: **월하의 해석이 열렸어요.** 주 버튼 **내 해석 읽기**, 보조 **결제 내역**. 실제 복원 방식과 열람 조건 안내.

읽은 뒤 **오늘 해볼 문장 저장하기**. 고양이가 한 번 발도장을 찍는다. 다른 상품 판매는 읽기 완료 이후 선택 영역. 기존 하루 구매 제한·재회 쿨다운·거절한 인물 재권유 제한을 보존한다.

## 5. ‘팩폭’ 콘텐츠 제작 명세

공식: **입력/전통 규칙 → 가능한 행동 패턴 → 장면 → 반복의 비용 → 예외 질문 → 실행 가능한 대안**. 인격을 공격하는 ‘너는 원래 이런 사람’보다 행동을 구체화한다. 아래는 톤을 검토하기 위한 예문이며 실제 이용자에게 적용하려면 조건과 출처가 필요하다.

| 고민 | 핵심 예문 | 확인 질문 / 무료 행동 | 유료에서 추가할 답 |
|---|---|---|---|
| 연애·관계 | “서운함을 말하기 전에, 상대를 이해할 이유부터 찾고 있지는 않나요?” | “최근에도 그랬나요?” / 서운했던 사실과 원하는 행동을 한 문장씩 분리 | 대화 시작 문장, 경계 설정, 다른 반응에 대한 선택지 |
| 일·커리어 | “잘하는 사람으로 남으려다, 내 일이 아닌 것까지 맡고 있지는 않나요?” | 담당 범위와 이번 주 추가 요청을 나눠 적기 | 업무 거절 문장, 우선순위 기준, 역할 조정 시나리오 |
| 돈·소비 | “금액보다 ‘이 정도는 괜찮다’는 순간이 반복되는지 살펴보세요.” | 최근 소비 하나의 상황·감정 기록 | 소비 기준·환경 바꾸기. 투자 종목/매수 시점 지시 제외 |
| 방향·선택 | “선택지를 못 찾는 걸까요, 하나를 고른 뒤 포기할 것이 부담스러운 걸까요?” | 지금 고를 수 있는 두 선택의 비용 적기 | 가치 기준표, 되돌릴 수 있는 작은 실험, 확인 시점 |
| 마음·생활 | “쉬는 시간에도 밀린 일을 계산한다면, 몸을 멈추는 것만으로는 쉬기 어려울 수 있어요.” | 오늘 끝낼 일 하나와 미룰 일 하나 구분 | 일상 경계·회복 습관. 질병 진단·수명 예측 제외 |
| 지난 관계 | “그 사람이 그리운지, 끝내 듣지 못한 답이 남은 건지 나눠볼까요?” | 원하는 답과 스스로 정할 수 있는 경계 구분 | 연락 전 점검표, 연락하지 않을 선택, 정리 문장. 상대 속마음·재회 확률 단정 제외 |

### 콘텐츠 데이터와 렌더링 계약

각 핵심 해석에 `insight_id`, `content_version`, `rule_id`, `required_features`, `excluded_if`, `concern_code`, `source_kind`, `source_ref`, `scene`, `counterexample`, `action`, `paid_extension_ids`를 둔다. 이 전체 은행을 프런트에 전송하지 않는다. 서버가 조건을 평가하고 필요한 결과만 렌더링한다.

출처 종류는 **사용자가 고른 상황 / 전통 명리 규칙 / 일반적인 실천 제안**으로 분리한다. 사용자가 말한 상황을 사주가 알아맞힌 것처럼 표현하지 않는다. 전통 규칙의 번호·한자·인용이 곧 경험적 정확성은 아니다.

시주가 필요한 내용은 시간 미상에서 제외한다. 데이터 없는 문장은 과장해서 채우지 않고 범위를 줄인다. 무료/유료의 명식과 기초 특징은 동일해야 한다. 결제를 유도하려고 무료 점수를 낮추거나 유료에서 갑자기 길하게 바꾸지 않는다.

20명은 말투만 다르게 하지 않는다. 각 인물마다 질문·관찰 관점·산출물을 매핑한다. 예: 월하=관계 대화, 훈장=학습/업무 구조, 행수=소비/관리 관점. **실제 기존 전문 분야를 검토한 뒤** 확정하며 개인별 가격 차이는 실제 열리는 깊이와 일치시킨다.

필수 검수 매트릭스: 공개 인물 전체 × 6고민 × 서로 다른 명식. 시간 미상, 절입 경계, 자시, 과거 표준시/서머타임, 양음력, 대운 시작 전 사례 포함. 원문 중복·의미 중복·서로 모순되는 행동 제안을 각각 검사한다. 예시 집합만 맞춘 고정 문장을 방지하기 위해 개발에 쓰지 않은 홀드아웃 명식을 둔다.

## 6. 종합점수 재설계

**사용자 사주 점수와 관리자 콘텐츠 점수, 실제 사업 지표를 합치지 않는다.**

사용자: `daily.py`의 점수는 기본값과 용신·합충 등의 가산/감산을 제한 범위로 자르는 규칙 지표다. 행복·성공·재회 확률이 아니다. 표시한다면 **오늘의 기운 지표**로 쓰고 산정 요인과 적용 범위를 설명한다. 근거 없는 새 ‘인생 종합점수’를 만들지 않는다. 낮은 점수를 보여주고 해결책 구매를 유도하지 않는다.

관리자: 기존 72점은 ‘자동 문장 검사 v1’로 남기고 각 항목의 검사법·표본·시각을 표시한다. ‘읽기 100’도 접근성 합격을 뜻하지 않게 설명한다.

새 관리자 첫 화면은 합산 점수 대신 다음 순서다.

| 구분 | 지표 | 통과 조건/판단 |
|---|---|---|
| 배포 차단 | 계산 회귀, 시간 미상 위반, 위험 단정, 노출 권한, 가격 불일치 | 명확한 위반 0건; 테스트 커버리지 함께 공개 |
| 콘텐츠 검수 | 구체성·조건 적합성·새 정보·실행 가능성·읽기 이해 | 2인 독립 1~5 평가와 불일치 검토. 초안 기준 각 중앙값 4 이상은 운영 목표이지 검증된 척도 아님 |
| 사용자 평가 | 상황 공감, 도움이 된 부분, 불일치 유형, 읽은 뒤 행동 의향 | 노출 전체/응답자 분모 별도, 무응답 제외 편향 표시 |

| 보호 지표 | 환불, 문의, 결제 실패, 반복 청구, 만족 악화 | 승자 판정 전에 함께 확인 |

## 7. 가격과 상품 구성

확인한 현행 코드: 개별 유료 인물 **9,900/12,900/15,900/19,900원**, 동자 무료. 전체 **99,000원**, 구독 **14,900원**. 개별은 인물별 가격이며 9,900원으로 일괄 표기하면 안 된다. `report.PRICE_RUNGS`는 12,900/15,900/19,900원 경계에 추가 내용을 연결한다.

일차 개편은 가격을 유지하고 **고민에 맞는 개별 해석을 주 상품**으로 배치한다. 전체 상품·구독은 ‘다른 열람 방식 보기’ 안에서 비교한다. 숨긴 구매 조건이 아니라 선택 가능한 다른 상품이다. 고가 전체 상품을 가짜 정상가 기준으로 쓰지 않는다.

구독은 현 코드상 30일 주기다. UI의 ‘달마다’와 달력상 매월 결제가 혼동되지 않도록 **30일마다 14,900원 자동 결제 / 다음 결제일 / 해지 경로 / 해지 후 남는 열람 기간**을 정확히 표시한다. 기본 선택하지 않는다. 구독의 깊이·기간 차이는 실제 권한 코드와 계약 테스트로 확정해서 비교표에 넣는다. 소스 주석에도 all/sub 범위 설명이 혼재하므로 주석만 믿고 ‘내용 완전 동일’이라고 판매하지 않는다.

후속 가격 실험은 콘텐츠·카피를 고정한 뒤 별도 진행한다. 서버 견적에 상품·가격 버전과 유효기간을 두고 표시 금액=주문 금액=PG 승인 금액을 보장한다. 결제율이 올라가도 객단가/환불 차감 매출이 떨어지면 목표를 달성했다고 보지 않는다.

방향: **먹색 밤 / 따뜻한 종이색 / 살구 금색 버튼 / 인물의 절제된 색감**. 세계관은 남기되 정보 주변의 장식 밀도를 낮춘다. 긴 본문 위에 영상·패턴을 겹치지 않는다.

정상 크기 텍스트 대비 4.5:1, 큰 텍스트 3:1을 확인한다. 제안 색상 계산값은 본문/패널 15.26:1, 보조문구/패널 8.11:1, 버튼 글자/버튼 10.05:1이다. 전체 화면 접근성 검증을 대신하지 않는다. WCAG 2.2 AA의 최소 타깃 기준은 예외 조건을 포함한 24 CSS px이며, 여기의 44px는 더 여유 있게 잡은 제품 목표다. [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [타깃 크기 해설](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

고정 CTA는 `safe-area-inset-bottom`을 반영하고 본문 하단 공간을 확보한다. 키보드가 열리면 입력을 가리지 않는다. 선택 상태를 색 하나로만 표현하지 않고 체크/텍스트를 함께 쓴다. 키보드 초점·200% 확대·320px 화면·화면낭독기·뒤로가기를 검수한다.

폰트는 사용 굵기와 한글 서브셋을 점검해 자체 호스팅하고 라이선스를 보존한다. 전체 한글 폰트를 여러 벌 선로딩하지 않는다. 첫 화면 주요 이미지 한 장만 우선순위를 높이고 나머지는 필요한 화면에서 로드한다. 목표는 모바일 실제 방문 p75 **LCP≤2.5초, INP≤200ms, CLS≤0.1**이며 현재 측정값이 아니다. [Core Web Vitals 기준](https://web.dev/articles/defining-core-web-vitals-thresholds).

CSS는 누적 override를 계속 덧붙이지 않고 토큰→공통 컴포넌트→화면 순서로 옮긴다. 기존 변경과 충돌을 피하도록 별도 개편 브랜치에서 화면 단위로 적용한다.

## 9. 고양이와 게이미피케이션

고양이 콘셉트 제안: **묘묘**, 먹색 몸·호박색 눈·작은 달 표식. 20명의 인물 사이를 이어주는 한 마리. 화면마다 품종·눈색·그림체가 바뀌지 않게 정면/측면/색상 참조 시트를 먼저 고정한다. 시안의 벡터 고양이는 동작 검토용이며 최종 생성 에셋이 아니다.

| 위치 | 상태/실제 트리거 | 움직임·카피 | 기능 |
|---|---|---|---|
| 첫 화면 | 기다림 | 한 번 눈인사, 1.2초 | 브랜드 친근감 |
| 고민 선택 | 선택 완료 | 고개 끄덕임, 0.6초 | 선택 피드백 |
| 정보 입력 | 실제 유효 입력 완료 | 발도장 1회 | 실제 진행 상황 |
| 시간 미상 | ‘몰라요’ 선택 | “아는 만큼만 알려줘도 돼요.” | 모르는 정보로 인한 포기 완화 |
| 계산 | 서버 응답 대기 | 조용히 앉은 정지 자세 | 가짜 진행률 없이 대기 안내 |
| 무료 결과 | 읽는 중 | 책 옆에서 잠자는 정지 자세 | 집중 방해 방지 |
| 행동 저장 | 저장 성공 | 책갈피에 발도장, 0.8초 | 저장 완료 피드백 |
| 결제 | 주문 확인/PG 이동 | 작고 정적인 모습 또는 숨김 | 가격·버튼 시선 경쟁 방지 |
| 구매 후 | 서버 승인 + 열람 권한 확인 | 작은 축하 1회, 1.2초 | 성공 상태 확인 |
| 재방문 | 저장한 문장 존재 | 책갈피 옆 정지 자세 | 이전 내용으로 복귀 |

동시에 1마리, 본문/CTA와 겹치지 않음, 자동 음성 없음, 반복 상호작용은 최소 15초 간격으로 제한한다. `prefers-reduced-motion`이면 정지 이미지와 텍스트로 같은 정보를 준다. 장식 이미지는 빈 alt, 의미 있는 상태는 별도의 텍스트로 전달한다.

무료 보상: 고민 선택·정보 완료·첫 해석 열람의 **실제 3단계** 발도장. 읽고 행동을 저장하면 개인 책갈피가 완성된다. 결제액·매일 방문·연속 결제에 따른 랜덤 보상은 넣지 않는다. 방문하지 않았다고 고양이를 굶기거나 진행을 초기화하지 않는다.

검증: 고양이 정지형 vs 상태 반응형. 읽기 이해도, 입력 완료율, p75 INP, 결제 전환, ‘방해됐다’ 응답을 함께 본다. 귀여움의 효과 크기는 미정이다.

## 10. 1만 명 모델과 지표 정의

아래는 **방문자 1만 명을 가정한 산술 시나리오**다. 현재 결제율도 미래 예측도 아니다. 1명의 첫 구매만 계산하며 재구매·구독 갱신은 제외한다. 원 데이터와 재현 코드는 문서 상단 링크에 있다.

| 단계 | 보수 가정 | 중간 가정 | 개선 가정 |
|---|---:|---:|---:|
| 신규 방문 | 10,000 | 10,000 | 10,000 |
| 입력 시작 | 5,000 | 6,000 | 6,500 |
| 계산 완료 | 3,250 | 4,500 | 5,200 |
| 무료 핵심 해석 읽음 | 2,113 | 3,375 | 4,160 |
| 상품 확인 | 951 | 1,856 | 2,496 |
| 결제 시작 | 190 | 464 | 699 |
| 서버 승인 | 171 | 432 | 664 |
| 방문→결제 | 1.71% | 4.32% | 6.64% |
| 모두 15,900원 구매 가정 매출 | 약 272만 원 | 약 686만 원 | 약 1,056만 원 |

단계별 반올림 전 수에 조건부 전환율을 곱한다. PG 수수료·세금·광고비·운영비 차감 전이며 순이익이 아니다. 환불 5% 가정 차감액은 JSON에 별도 수록했다. 실제 단가 믹스와 환불 데이터가 들어오면 대체한다.

**주 지표:** 실험에 최초 배정된 신규 유효 방문자 중, 노출 후 7일 안에 서버에서 첫 결제 승인된 방문자의 비율. 익명 브라우저 ID는 실제 사람 수와 같지 않으므로 보고서에 단위를 밝힌다. 직원·봇 제외 규칙과 배정 자격은 실험 전 고정한다.

**함께 판단:** 방문당 승인 매출, 7일 환불 차감 매출(관찰 기간이 찬 코호트만), 30일 환불 추적, 결제 후 첫 열람, 문의율, 실패율, 구독 해지율. 구독 갱신과 일회성 매출은 나눠 본다.

분해식: 방문→입력 × 입력→계산 × 계산→무료 읽음 × 무료→상품 × 상품→결제 시작 × 시작→승인. 먼저 가장 큰 사용자 손실과 개선 비용을 함께 본다. 앞 단계가 늘었지만 저의도 방문만 늘어 매출이 줄 수 있으므로 최종 지표가 필요하다.

### 실험에 1만 명이 충분한가

독립 베르누이, 양측 α=.05, 검정력 .8, 50:50 배정의 정규 근사에서 **3%→4%**를 감지하려면 약 **군당 5,301명**, **3%→3.6%**는 **군당 13,914명**이 필요하다. 기준 3% 자체가 가정이다. 1만 명이면 작은 차이까지 확인하거나 여러 안을 동시에 평가하기 어렵다.

첫 전체 경험 실험 하나에 트래픽을 집중한다. 실험 기간은 최소한 주간 패턴을 포함하고 필요한 표본·전환 관찰 기간을 채운다. 중간에 p값이 작아졌다고 멈추지 않는다. 배정 비율 이상(SRM), 이벤트 유실, 기기/유입원 불균형을 먼저 검사한다. 실험 전 최소 유의미 효과·중단 조건·보호 지표를 기록한다.

후속 순서: 무료 해석의 구체성 → 상품 설명 → 입력 배치 → 고양이 → 가격. 서로 겹치는 이용자 실험은 격리하거나 상호작용을 분석할 수 있을 때만 실행한다.

## 11. 계측·결제·용량 구현 명세

이벤트 제안: `experiment_exposed`, `input_started`, `chart_completed`, `free_insight_viewed`, `insight_feedback`, `offer_viewed`, `checkout_started`, **서버** `payment_approved`, `entitlement_granted`, `payment_refunded`, `paid_report_opened`. 읽음은 특정 카드 노출과 실제 머문 시간 등 운영 정의를 명시하고, 인간의 이해를 증명하는 지표로 취급하지 않는다.

허용 속성은 난수 이벤트 ID, 가명 방문 키, 시간, 화면/단계 코드, 실험/안 코드, 콘텐츠/가격 버전, 카테고리형 오류 코드, 서버의 금액/통화 등으로 제한한다. 현재 숫자만 받는 API에서 새 속성이 자동으로 저장된다고 가정하지 않는다. 프런트·백엔드 스키마·DB 마이그레이션을 함께 변경한다. 생년월일·이름·원문 고민·명식 ID·결제 인증 키는 분석에 넣지 않는다. 방문-주문 매핑은 서버에서 접근·보관 기간을 제한한다.

같은 사용자의 단계 순서, 최초 노출 코호트, 7일 전환 창을 적용하고 이벤트 ID/주문 ID로 중복 제거한다. 직접 상품 진입·재방문·복원은 별도 경로로 보고 첫 방문 퍼널의 이전 단계를 억지로 채우지 않는다. 클라이언트 `pay_done`은 화면 UX 참고용이며 매출 원장은 서버 주문이다.

결제 P0 검증 항목:

1. 주문 소유권: 요청 세션과 주문 소유자를 비교하는 전 경로 확인. 감사한 confirm 함수에서는 명시적 비교를 확인하지 못했으므로 재현 테스트로 검증한다. 현재 취약점 악용이 입증됐다는 뜻은 아니다.
2. 승인 중복: pending→confirming→paid 상태 전이를 원자적으로 만들고, 동시 요청·재전송·웹훅 중복에도 권한과 구매 횟수는 한 번만 반영한다.
3. PG 요청 타임아웃: 승인 실패로 즉시 단정하지 않고 주문 조회로 복구. 해당 Toss API의 멱등 처리 계약을 확인해 동일 주문 재시도에 적용한다.
4. 표시 가격=서버 견적=승인 금액. 조작한 클라이언트 값은 거절한다. 현재 서버 가격 계산은 유지한다.
5. 승인 성공 후 권한 부여 실패, 모바일 앱 복귀, 창 닫기, 재접속, 취소·환불 후 권한, 구독 해지·복원까지 테스트한다. 기존 복원/구독 기능을 삭제하지 않는다.

인증 후 서버 승인이 필요하다는 흐름과 모바일 리다이렉트 처리는 [Toss 결제창 통합 문서](https://docs.tosspayments.com/guides/v2/payment-window/integration), 조회·승인·취소 계약은 [공식 API 레퍼런스](https://docs.tosspayments.com/reference)를 기준으로 한다. 결제 수단은 실제 가맹 계약에서 활성화된 것만 보여준다.

**1만 방문자≠1만 동시 접속.** 하루 1만 방문이면 평균 약 0.116방문/초다. 방문당 API 10회 가정은 평균 1.16요청/초, 20배 피크는 약 23요청/초다. 광고로 10분에 1만 명이 몰리면 약 16.7방문/초, 같은 가정에서 약 167요청/초다. 실제 호출 수·도착 분포·응답 시간으로 다시 계산해야 한다.

용량 시험은 별도 환경에서 계산·무료·tiers·승인 모의 요청 비율을 섞어 단계 상승 부하로 진행한다. 30RPS의 일상 피크 가정부터 광고 가정 170RPS까지 p95/p99, 오류율, DB 연결, CPU, 큐 대기와 캐시 적중을 측정한다. 실제 PG 과금 호출에 부하를 가하지 않는다. 이번 작업에서는 이 부하 시험을 실행하지 않았다.
